# Deployment procedure

**Blocked externally:** designate the repository, Vercel project/plan, domain/DNS, separate Supabase environments, Paymob merchant, Meta number/app, Resend sender, Mux environment, monitoring receiver and staff owner before following external steps. Record the verified identities in a restricted release record. Do not reuse accounts discovered in another project.

1. Record the candidate Git commit, migration head and all test results. Run `npm ci`, lint, typecheck, all domain/security/concurrency tests, locale parity, API generation, all browser engines and build.
2. In owner-designated staging, create a restricted `tourism_app` runtime role and a separate migration role. Keep `app` outside exposed Data API schemas. Apply ordered migrations with `MIGRATION_DATABASE_URL`. Do not run the synthetic seed in production.
3. Configure Supabase Auth invite-only access and exact application redirect allowlists. Create the private `tourism-private` bucket and confirm public=false. Bootstrap the designated initial owner through a reviewed migration/admin procedure; require MFA before staff work.
4. Configure staging secrets through the platform secret store using `.env.example` as the inventory. Use Paymob sandbox, allowlisted messaging recipients, isolated storage/database/provider environment and `STAGING_ISOLATION_CONFIRMED=true`. Run `npm run verify:release`.
5. Deploy staging through the designated Vercel project. Verify ready/live endpoints, all locale pages, private storage denial, no-store responses, nonce CSP, secure cookies and provider callback signatures. Exercise the complete designated guest/staff journey with sandbox payments and actual email/WhatsApp callbacks. Record accepted versus delivered separately.
6. Load approved business content through the staff workflow. Approve identity, prices, policies, calendars, property units, rights/subject consent and all enabled locale translations. Record staff UAT and backup/storage restoration evidence. Keep 3D disabled while its recorded gates fail.
7. Configure production secrets separately, `APP_ENV=production`, `DEMO_MODE=false`, approved flags and retention days. `verify:release` validates environment and persisted data; `verify:production` intentionally rejects local/default configurations. The release check is necessary but does not replace owner UAT or provider evidence.
8. Use the host's exact returned domain/DNS instructions. Preserve unrelated email records. Verify canonical redirects, HTTPS, Auth redirects, Paymob/Mux/Meta/Resend callback URLs and authenticated worker/monitor/retention cron endpoints.
9. Promote the verified deployment only after staging and owner gates pass. Record the exact URL, Git commit, migration version and rollback deployment. Run read-only production checks, then the owner-authorized live transaction on the designated amount and test contacts. Never charge arbitrary guests.

The cron schedule requires a suitable commercial plan: worker each minute, monitor every five minutes, retention daily at02:30UTC. Configure `CRON_SECRET` with at least32 random characters and `MONITORING_ALERT_URL` to the approved HTTPS destination. Region `fra1` is a deployment default to review against the designated database region.

Production launch remains incomplete until its real URL and provider journey are verified and entered in `docs/RELEASE_REPORT.md`.
